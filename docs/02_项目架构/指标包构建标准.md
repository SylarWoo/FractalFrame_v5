# 指标包构建标准

本文定义 FractalFrame 后续指标系统的构建方向。当前已经不再采用“全量后台预计算指标包”的方案。

新的原则是：StoreV6 只保存干净 K 线；指标属于页面加载器和页面运行器的一部分。实时页指标服务实时看盘，历史页指标在页面加载完成后按当前参数临时一次性计算并渲染。指标结果不固化为历史仓库数据。

## 1. 核心结论

1. StoreV6 不保存指标结果。
2. 实时页和历史页指标必须隔离。
3. 历史页加载时可以临时一次性计算指标。
4. 缩放、拖动只重绘，不重新计算指标。
5. 指标参数变化时，当前页面重新计算，其他页面不被污染。

## 2. 为什么删除全量后台指标方案

旧方案认为历史指标应该提前在后台全部算好，再按全局 K 线索引缓存或入库。这个方案现在不再作为主线，原因如下：

1. 指标参数随时会变，提前固化意义不大。
2. 不同指标的 warmup、lookahead、依赖参数不同，后台全量维护成本高。
3. StoreV6 的职责应该保持纯净，只负责 K 线身份、OHLCV、开休市扩展信息和分页基础。
4. 看图时每页只有 2000 到 2500 根 K 线，前台临时计算足够轻。
5. 后台指标全量化会让“数据仓库”和“视图状态”耦合，后续更难维护。

所以后续不再建设统一的后台历史指标库。只有少数特殊指标，例如 MMF_v3 已有后台计算链路的部分，可以作为特殊链路保留，但不能反向要求所有指标都后台化。

## 3. 页面级指标运行器

后续新增模块建议命名为：

```text
Page Indicator Runtime
页面指标运行器
```

它属于页面加载器的一部分，不属于 StoreV6 仓库。

职责边界：

```text
输入：当前页面 K 线、warmup K 线、当前指标参数、当前页面 pageKey
处理：按指标定义临时计算当前页面指标
输出：交给 KLineChart 渲染的指标实例和页面级指标快照
缓存：只做页面运行缓存，不写入 StoreV6
```

页面指标运行器只服务当前打开页面。页面切换后，新的页面拥有自己的指标运行上下文。

## 4. 实时页指标

实时页是活动页面，永远是第一页。

当前约定：

```text
实时页基础窗口：2000 根 K 线
实时页增长上限：约 2500 根，触发整理后重置
数据来源：StoreV6 最新 K 线 + 实时 tick 更新
指标计算：KLineChart 前台计算为主
```

实时页指标状态需要本地缓存：

```text
已加载指标列表
每个指标的参数
副图 pane 高度
主图指标/副图指标的运行状态
实时页 pageKey
```

用户在实时页加载、卸载、修改指标参数时，只更新实时页指标缓存。切到历史页后，实时页仍然作为后台活动窗口保持自己的实时数据和指标状态。切回实时页时，按实时页缓存恢复。

## 5. 历史页指标

历史页是静态页面。当前阶段已经先做到：历史页不加载任何指标，只显示裸 K。

下一步规划：

1. 历史页加载完成后，页面指标运行器读取该页 K 线。
2. 按当前已选择指标和参数，临时一次性计算指标。
3. 计算结果只绑定当前历史页 pageKey。
4. KLineChart 只负责渲染当前页结果。
5. 缩放、拖动、十字光标移动只重绘，不重新计算。

历史页指标不写入 StoreV6，也不变成后台固定数据。

## 6. PageKey 隔离规则

所有页面指标上下文必须绑定 pageKey。pageKey 是实时页和历史页隔离的核心。

建议结构：

```text
symbol
period
mode: realtime | history | jump
pageIndex
timeFrom
timeTo
rows
settingsHash
```

示例：

```text
XAUUSD:M5:realtime:1:latest:2000:settingsHash
XAUUSD:M5:history:2:2026-05-20T00:00:00:2026-05-28T16:35:00:2500:settingsHash
```

强制规则：

1. 实时页指标缓存不能被历史页覆盖。
2. 历史页 A 的指标缓存不能被历史页 B 覆盖。
3. 参数变化后，settingsHash 变化，当前页面重新计算。
4. K 线范围变化后，pageKey 变化，当前页面重新计算。
5. 缩放和拖动不能改变 pageKey，也不能触发重新计算。

## 7. K线身份对齐规则

指标结果必须和 StoreV6 的 K 线唯一身份对齐。指标可以临时计算，但不能只依赖数组下标，也不能把 warmup 区、display 区、历史页和实时页的数据混在一起。

统一身份：

```text
barId / barKey = symbol + period + openTime
```

指标输入要求：

```text
每根 K 线必须携带 symbol、period、time、barKey。
实时页、历史页、warmupRows、displayRows 使用同一套 barKey 规则。
进入指标计算前，页面加载器要确认 K 线时间顺序和 barKey 唯一性。
```

指标输出要求：

```text
每条指标结果必须带 barKey。
可以保留 sourceIndex 作为辅助信息，但不能只靠 sourceIndex 对齐。
如果指标来自后台计算或快照，也必须返回 barKey/time。
```

渲染前对齐规则：

```text
当前页面 displayRows 先建立 barKey -> rowIndex 映射。
指标结果按 barKey 找回当前页面对应 K 线。
找不到 barKey 的指标结果直接丢弃或标记为 orphan，不渲染到图上。
同一个 barKey 出现多条同类指标结果时，按指标规则合并或按优先级处理。
```

历史页尤其要遵守这条规则。因为历史页指标计算会使用：

```text
calculationRows = warmupRows + displayRows + lookaheadRows
```

但最终只能渲染 `displayRows` 对应的结果。截取结果时必须按 `barKey` 回落到当前页面，不能简单按数组下标切片。

这条规则的目标是避免：

```text
指标画到错误 K 线上。
warmup 数据污染显示页。
历史页和实时页互相错位。
后台指标返回结果与前台页面数据无法对齐。
```

## 8. 指标计算触发条件

允许触发重新计算：

```text
加载指标
卸载指标
修改指标参数
切换品种
切换周期
切换页面
页面 K 线范围变化
实时页新增 K 线或当前 K 线更新
```

不允许触发重新计算：

```text
缩放图表
左右拖动
移动十字光标
改变可视窗口
普通重绘
历史页之间的无关缓存变化
```

这样可以保证手感稳定。缩小以后变重的问题，后续优先检查是否有指标在 zoom/drag 时重复 calc，而不是做“重指标分级”。

## 9. Warmup 规则

虽然历史页显示 2500 根，但指标计算可能需要更多上下文。

页面加载器需要提供：

```text
displayRows：当前页面真正显示的 K 线
warmupRows：为了计算指标向左补充的 K 线
lookaheadRows：少数需要右侧确认的指标使用
calculationRows：warmupRows + displayRows + lookaheadRows
```

指标运行器使用 calculationRows 计算，但只把 displayRows 对应的结果交给当前页面渲染。

## 10. 指标状态缓存

指标缓存是视图运行缓存，不是数据仓库。

建议缓存结构：

```ts
type PageIndicatorRuntimeCache = {
  pageKey: string
  symbol: string
  period: string
  mode: 'realtime' | 'history' | 'jump'
  pageIndex: number
  indicators: Array<{
    key: string
    settingsHash: string
    settings: Record<string, unknown>
    paneId?: string
    paneHeight?: number
  }>
  calculatedAt: string
}
```

实时页缓存可以持久化到本地，用来刷新后恢复。历史页缓存优先放内存，后续如果需要提升翻页体验，再做小容量 LRU 缓存。

## 11. 特殊指标链路

普通指标优先使用 KLineChart 前台计算，例如：

```text
MA
MACD
RSI
Stoch
DPO
SQZMOM
VDO
TSI
VI
AO
VMI
VWAP
Vol
```

已有特殊链路可以保留，例如：

```text
MMF_v3 后台计算/快照链路
MR 区间结构计算
```

但特殊链路也必须遵守 pageKey 隔离，不能污染实时页，也不能要求所有历史页提前全量后台计算。

## 12. 当前实现状态

截至当前设计：

1. StoreV6 数据底座已经转向唯一 K 线身份和分页规划。
2. 实时页已经具备实时缓存。
3. 历史页当前先隔离为裸 K，不加载指标。
4. 实时页允许加载指标，并保留本地指标状态。
5. 下一步要做的是历史页的页面级一次性指标计算。

## 13. 后续实现顺序

建议明天继续按这个顺序做：

1. 建立 `Page Indicator Runtime` 模块。
2. 明确实时页指标缓存结构。
3. 明确历史页指标临时计算入口。
4. 给 `ChartCoreHost` 增加页面指标运行域。
5. 历史页加载完成后按 pageKey 计算并渲染指标。
6. 确认缩放、拖动只重绘，不重新计算。
7. 再接回 MMF_v3、MR 等特殊指标链路。

最终目标：

```text
StoreV6：只管干净 K 线和分页基础。
实时页：活动窗口，指标跟随实时缓存运行。
历史页：静态窗口，进入页面时按当前参数临时计算指标。
KLineChart：负责渲染和轻量前台指标，不承担全量历史后台计算。
```
