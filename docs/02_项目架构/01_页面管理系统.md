# 页面管理系统

> 目标：把“分页、计算上下文、指标计算、数据整理、窗口切片、KLineChart 渲染”拆成 6 个明确模块。每个历史页先形成完整页面数据包，KLineChart 只负责渲染窗口切片，不再负责页级指标计算和临时对齐。

## 1. 总体判断

可以按 6 个方向形成具体系统，而且这 6 层比原来的 3 层更准确。

原来的 3 层是：

```text
数据管理 -> 窗口管理 -> 渲染
```

现在应该细化为：

```text
1. 数据分页模块
2. 数据计算管理模块
3. 指标计算模块
4. 数据整理模块
5. 窗口管理模块
6. 指标加载限制模块
7. KLineChart 渲染模块
```

前 4 个模块共同组成“页面数据包底座”。第 5 个模块负责从页面包里取窗口切片。第 6 个模块负责按指标预算裁剪要渲染的内容。第 7 个模块只画图。

核心链路：

```text
MT5/StoreV5 K线
  -> 数据分页模块
  -> 数据计算管理模块
  -> 指标计算模块
  -> 数据整理模块
  -> PageDataPackage
  -> 窗口管理模块
  -> ChartRenderSlice
  -> 指标加载限制模块
  -> BudgetedRenderSlice
  -> KLineChart 渲染模块
```

## 2. 模块一：数据分页模块

### 2.1 职责

数据分页模块只负责把 StoreV5/MT5 数据按规则切成页。

它回答的问题是：

```text
第 1 页是哪段 K 线？
第 2 页是哪段 K 线？
第 N 页的 timeFrom/timeTo/rows 是什么？
历史页每页是 2500 根，还是以后继续可配置？
```

它不负责指标计算，也不负责 warmup。

### 2.2 输入

```ts
type PagePartitionRequest = {
  symbol: string
  period: string
  historyPageSize: number // 当前建议 2500
  realtimePageSize: number // 当前建议 2000
  totalRows?: number | null
  realtimeSnapshot?: {
    rows: number
    timeFrom: number
    timeTo: number | null
  } | null
}
```

### 2.3 输出

```ts
type PagePartition = {
  symbol: string
  period: string
  historyPageSize: number
  realtimePageSize: number
  livePage: LivePagePartition | null
  historyPages: HistoryPagePartitionItem[]
}

type LivePagePartition = {
  pageType: 'live'
  limit: number
  rows: number
  timeFrom: number | null
  timeTo: number | null
}

type HistoryPagePartitionItem = {
  pageType: 'history'
  pageNo: number
  pageSize: number
  rows: number
  fromGlobalIndex: number
  toGlobalIndex: number
  timeFrom: number | null
  timeTo: number | null
}
```

### 2.4 规则

1. 实时页和历史页必须分开。实时页是 `LivePagePartition`，历史页是 `HistoryPagePartitionItem[]`。
2. 实时页建议只保留最近 2000 根，用于看盘和前台轻量指标。
3. 历史页建议按 2500 根一页切分，用于历史复盘、后台指标和页面预备数据包。
4. 每个历史页只定义 display K 线范围。
5. 不在分页模块里混入指标 warmup。
6. 分页结果要能缓存成页面清单，避免每次打开右侧面板都重建。
7. 分页模块只维护页面范围，不维护 K 线唯一身份。K 线唯一身份属于全局索引模块。

### 2.5 实时页和历史页分离

实时页不是历史第一页。实时页是独立看盘块，历史页是稳定复盘块。

```text
LivePage
  -> 最近 2000 根
  -> 前台轻量指标
  -> tick 更新
  -> 看盘优先

HistoryPageManifest
  -> 每页 2500 根
  -> 后台历史指标
  -> 按 barKey/globalIndex 对齐
  -> 复盘、回测、历史浏览优先
```

实时页新增 K 线时，不应该把实时页和历史页混成同一个数组下标系统。正确做法是：

```text
1. 新 K 线进入 StoreV5。
2. 全局索引模块追加 barKey/globalIndex。
3. LivePage 重新取最近 2000 根。
4. HistoryPageManifest 按新的 globalIndex 范围重新切分。
5. 已存在历史指标仍然按 barKey 对齐，不因为 pageNo 变化而错位。
```

### 2.6 页面清单重建机制

当新的实时 K 线成立后，K 线总数增加，历史页切分点可能变化。例如原来刚好 5 页，新增后可能变成 5 页半。这时需要重建的是页面清单，不是重建全局索引，也不是重算全部历史指标。

页面清单可以理解为一张很轻的 manifest 表：

```ts
type HistoryPageManifestRow = {
  symbol: string
  period: string
  pageNo: number
  pageSize: number
  fromGlobalIndex: number
  toGlobalIndex: number
  timeFrom: number
  timeTo: number
  rows: number
  version: number
}
```

重建页面清单只是在做范围切分：

```text
totalRows = 640000
pageSize = 2500
pageCount = ceil(totalRows / pageSize)

for pageNo in 1..pageCount:
  fromGlobalIndex = ...
  toGlobalIndex = ...
```

这个操作不慢。64 万根 K 线按 2500 一页，大约 256 页。重建 256 条页面范围记录，比重算 64 万根指标轻很多。

### 2.7 为什么重新分页不会很复杂

重新分页本身只是元数据变化。

```text
会变：
pageNo
fromGlobalIndex
toGlobalIndex
timeFrom/timeTo
pageCount

不会变：
barKey
time
K 线 OHLCV 原始记录
历史指标绑定关系
已经算好的 HistoryIndicatorRow
```

所以复杂度不在分页，而在两件事：

```text
1. 不能让指标绑定 pageIndex 或数组下标。
2. 不能让 KLineChart 在缩放、拖动时重新计算页级指标。
```

只要指标绑定 `barKey/time/globalIndex`，重新分页就只是重新生成页面范围。切到某个历史页时，再按这个页面范围去取 K 线和同一批 barKey 的指标即可。

### 2.8 推荐分页方向

历史页建议采用右侧锚定，也就是越靠近当前行情的历史页越优先稳定。

```text
LivePage：最近 2000 根，独立存在。
HistoryPage 1：LivePage 之前最近的 2500 根历史 K 线。
HistoryPage 2：再往左的 2500 根历史 K 线。
HistoryPage N：更早的历史 K 线。
```

这样做的好处：

```text
看盘时始终先进入 LivePage。
从实时页往左翻，进入最近历史页。
新增 K 线后，右侧历史页边界可能更新，但 K 线身份不变。
用户回到历史页时，按新的 page manifest 取数据即可。
```

如果要让“旧的第 2 页”在新增 K 线后仍然能回到同一批 K 线，可以额外保存 `pageSnapshotKey`。但默认浏览系统不需要锁死旧页面号，只需要保证 K 线和指标按全局索引对齐。

## 3. 模块二：数据计算管理模块

### 3.1 职责

数据计算管理模块负责把“显示页”扩展成“计算页”。

它回答的问题是：

```text
当前历史第 2 页显示 2500 根。
指标计算需要前面多少根 warmup？
需要后面多少根 lookahead？
displayRows 在 calculationRows 里的起始 index 是多少？
每根 K 线的 barKey/sourceIndex 怎么建立？
```

这个模块不再次分页。它只是围绕某个已确定页面，建立计算上下文和索引。

### 3.2 核心数据

```ts
type PageCalculationFrame = {
  key: string
  symbol: string
  period: string
  pageIndex: number
  realtime: boolean

  displayRows: ChartBarRow[]      // 当前历史页显示的 2500 根，实时页显示最近 2000 根
  warmupRows: ChartBarRow[]       // 前置上下文，不显示
  lookaheadRows: ChartBarRow[]    // 后置确认数据，不显示
  calculationRows: ChartBarRow[]  // warmup + display + lookahead
  displayOffset: number           // displayRows[0] 在 calculationRows 中的位置
}

type ChartBarRow = {
  barKey: string
  sourceIndex: number
  time: number
  timestamp: number
  open: number
  high: number
  low: number
  close: number
  volume?: number
}
```

### 3.3 索引规则

必须同时保留两套 index：

```text
calculationIndex: 在 calculationRows 中的位置
displayIndex: 在 displayRows 中的位置
```

二者关系：

```text
calculationIndex = displayOffset + displayIndex
displayIndex = calculationIndex - displayOffset
```

所有指标都应该知道自己基于 calculationRows 计算，但最终结果要能回到 displayRows。

### 3.4 设计原则

1. warmup/lookahead 是计算上下文，不是显示分页。
2. 数据计算管理模块只准备索引和数据范围，不直接算指标。
3. 每根 K 线必须有稳定 `barKey`。
4. 指标结果优先按 `barKey` 对齐，其次才按 index。

## 4. 模块三：指标计算模块

### 4.1 职责

指标计算模块负责把 PageCalculationFrame 交给每个指标包计算。

它回答的问题是：

```text
当前页面启用了哪些指标？
每个指标需要哪些输入？
每个指标产出多少行？
指标结果是 calculationRows 长度，还是 displayRows 长度？
指标参数和版本如何生成 hash？
```

### 4.2 指标包接口

每个指标应该像一个独立包：

```ts
type PageIndicatorPlugin<InputSettings, OutputRow> = {
  key: string
  version: string
  calculate: (input: PageIndicatorInput<InputSettings>) => Promise<PageIndicatorOutput<OutputRow>>
}

type PageIndicatorInput<Settings> = {
  frame: PageCalculationFrame
  settings: Settings
  dependencies: PageIndicatorTables
}

type PageIndicatorOutput<Row> = {
  key: string
  version: string
  rows: Row[]
  rowScope: 'calculation' | 'display'
  byBarKey?: Record<string, Row>
}
```

### 4.3 后台指标方向

后续指标应逐步后台化：

1. 前端只发 PageCalculationFrame 的 OHLCV 和指标参数。
2. 后台指标引擎计算 MMF_V3、MR、MA、VWAP、Stoch、VDO、VMI、TSI 等。
3. 返回指标表。
4. 前端只做缓存、对齐、渲染。

短期允许部分指标仍在前端计算，但接口要按“指标包”模式设计，后续才能迁移到后台。

### 4.4 指标依赖

指标之间可以有依赖，例如 MMF_V3 可能依赖：

```text
Stoch
VDO
VMI
TSI
MR
VWAP
MA
```

指标计算模块应该按依赖图执行：

```text
基础指标 -> 复合指标 -> 策略信号
```

不允许某个指标在 KLineChart `calc` 里偷偷重算依赖。

## 5. 模块四：数据整理模块

### 5.1 职责

数据整理模块负责把 K 线、计算上下文、指标结果统一整理成一个页面数据包。

它回答的问题是：

```text
K线表在哪里？
指标表在哪里？
每个指标结果和哪根 K 线对应？
这一页是否 ready？
这个包的缓存 key 是什么？
```

### 5.2 页面数据包

```ts
type PageDataPackage = {
  key: string
  symbol: string
  period: string
  pageIndex: number
  realtime: boolean

  frame: PageCalculationFrame
  indicatorTables: PageIndicatorTables

  status: 'loading' | 'calculating' | 'ready' | 'failed'
  settingsHash: string
  calculatedAt?: string
  error?: string
}

type PageIndicatorTables = {
  MMF_V3?: IndicatorTable<MmfV3IndicatorRow>
  MR_M5?: IndicatorTable<MrIndicatorRow>
  MR_M30?: IndicatorTable<MrIndicatorRow>
  MA?: IndicatorTable<MaIndicatorRow>
  VWAP?: IndicatorTable<VwapIndicatorRow>
  Stoch?: IndicatorTable<StochIndicatorRow>
  VDO?: IndicatorTable<VdoIndicatorRow>
  VMI?: IndicatorTable<VmiIndicatorRow>
  TSI?: IndicatorTable<TsiIndicatorRow>
}

type IndicatorTable<Row> = {
  rows: Row[]
  rowScope: 'calculation' | 'display'
  byBarKey: Record<string, Row>
}
```

### 5.3 整理规则

1. 所有输出必须写入同一个 PageDataPackage。
2. 包内必须保留 displayOffset。
3. 包内必须保留 settingsHash 和指标版本。
4. 如果指标是 calculationRows 长度，窗口取值时要加 displayOffset。
5. 如果指标是 displayRows 长度，窗口取值时直接用 displayIndex。
6. 不允许渲染层再自己推导指标对齐关系。

## 6. 模块五：窗口管理模块

### 6.1 职责

窗口管理模块负责在 PageDataPackage 里找当前要渲染的切片。

它回答的问题是：

```text
当前屏幕能看到多少根 K 线？
当前 visibleFrom/visibleTo 是多少？
需要前后多取多少 buffer？
应该从 PageDataPackage 里切哪一段？
快到页边界时是否要预加载相邻页？
```

### 6.2 窗口结构

```ts
type ChartRenderWindow = {
  pageKey: string
  visibleFrom: number
  visibleTo: number
  bufferBefore: number
  bufferAfter: number
  renderFrom: number
  renderTo: number
}

type ChartRenderSlice = {
  pageKey: string
  rows: ChartBarRow[]
  indicators: PageIndicatorTables
  renderFrom: number
  renderTo: number
}
```

### 6.3 手电筒模式

页面包是一整页数据库，窗口是手电筒。

```text
页面包：2500 根 displayRows + warmup + indicatorTables
当前可见：500 根
buffer：前后各 50 根
实际渲染：约 600 根
```

缩放只改变 visibleCount。拖动只改变 visibleFrom/visibleTo。

指标不重算，只取切片。

## 7. 模块六：指标加载限制模块

### 7.1 职责

指标加载限制模块负责控制“某个指标一次最多渲染多少”。

它回答的问题是：

```text
当前窗口里有多少根 K 线？
这个指标属于普通线、marker，还是背景类指标？
当前缩放级别下，这个指标最多允许画多少段/多少点/多少 marker？
超过预算时，优先保留右侧近期数据，还是保留当前光标附近数据？
```

这个模块不负责计算指标值。指标值已经在 PageDataPackage 里算好了。

### 7.2 为什么需要这个模块

裸 K 线缩小到 3000 根不卡，说明 KLineChart 本体可以承受大量蜡烛。

真正卡的是复杂指标渲染：

```text
MR 背景区间
VWAP 背景填充
MMF_V3 大量 marker
Volume Profile / 支撑阻力背景
```

这些指标即使不重算，只要一次画太多，也会卡。

所以必须分开：

```text
指标计算：可以完整页计算
指标存储：可以完整页保存
指标渲染：必须按预算限制
```

### 7.3 指标分类

```ts
type IndicatorRenderClass =
  | 'line'       // MA、RSI、Stoch、TSI 等普通线
  | 'histogram'  // MACD、AO、VMI 等柱状图
  | 'marker'     // MMF_V3 信号点
  | 'background' // MR、VWAP fill、Volume Profile、支撑阻力背景
```

### 7.4 渲染预算

```ts
type IndicatorRenderBudget = {
  className: IndicatorRenderClass
  maxBars?: number
  maxSegments?: number
  maxPoints?: number
  maxMarkers?: number
  priority: 'right' | 'visible' | 'cursor' | 'manual'
  denseMode: 'full' | 'reduced' | 'minimal' | 'hidden'
}
```

### 7.5 MR 预算规则

MR 属于背景/区间指标。

M5 上 MR-M5 是 H4 一段：

```text
4小时 = 48 根 M5
50 个 MR 段 ≈ 2400 根 M5
```

建议默认：

```ts
const mrRenderBudget = {
  maxSegments: 50,
  priority: 'right',
}
```

规则：

```text
当前窗口 MR 段 <= 50：
  全部渲染

当前窗口 MR 段 > 50：
  从 visibleTo 往左取最近 50 段
  更左侧旧 MR 不渲染

用户放大某个日期：
  如果窗口内 MR 段 <= 50
  该窗口重新铺满 MR
```

这不是“永远只画最新 50 个”，而是：

```text
每次根据当前窗口取最多 50 个，默认右侧优先。
```

### 7.6 VWAP 预算规则

VWAP 属于连续线 + 背景填充指标。

建议：

```text
visibleBars <= 800:
  VWAP 主线 + 上下轨 + 填充

800 < visibleBars <= 1500:
  VWAP 主线 + 上下轨，不画填充

1500 < visibleBars <= 3000:
  只画 VWAP 主线，最多抽样 1000 点

visibleBars > 3000:
  只画最近 N 根 VWAP，或者隐藏 VWAP
```

预算结构：

```ts
type VwapRenderBudget = {
  maxPoints: number
  fillMaxPoints: number
  rightPriority: boolean
}
```

### 7.7 MMF_V3 marker 预算规则

MMF_V3 属于 marker 信号指标。

建议：

```text
visibleBars <= 800:
  完整显示 marker

800 < visibleBars <= 1500:
  只显示核心 marker

1500 < visibleBars <= 2500:
  只显示高优先级 marker，例如高低点、支撑阻力、背离

visibleBars > 2500:
  隐藏 MMF_V3 marker，或只显示极少量关键状态
```

marker 预算不是为了少算，而是为了少画。

### 7.8 输出

指标加载限制模块输入 `ChartRenderSlice`，输出 `BudgetedRenderSlice`。

```ts
type BudgetedRenderSlice = {
  pageKey: string
  rows: ChartBarRow[]
  indicators: BudgetedIndicatorTables
  renderFrom: number
  renderTo: number
  budgets: Record<string, IndicatorRenderBudget>
}
```

KLineChart 渲染模块只接收 `BudgetedRenderSlice`。

## 8. 模块七：KLineChart 渲染模块

### 8.1 职责

KLineChart 渲染模块只负责画 ChartRenderSlice。

它回答的问题是：

```text
我拿到了哪些 rows？
这些 rows 对应哪些指标 rows？
当前应该画蜡烛、marker、线段、overlay？
用户缩放/拖动后，把 visibleRange 告诉谁？
```

### 8.2 不允许承担的职责

KLineChart 不负责：

1. 数据分页。
2. warmup/lookahead 加载。
3. 页级指标计算。
4. 指标依赖计算。
5. K 线和指标对齐。
6. 跨页数据包管理。

### 8.3 渲染输入

```ts
type KLineChartRenderInput = {
  pageKey: string
  rows: ChartBarRow[]
  indicatorRows: BudgetedIndicatorTables
  renderFrom: number
  renderTo: number
}
```

### 8.4 指标渲染方式

KLineChart indicator 的 `calc` 不能再做复杂计算。

允许：

```text
calc = 从当前 ChartRenderSlice 里读取已算好的指标 row
draw = 按 row 绘制 marker/line/area
```

不允许：

```text
calc = 重新计算 MMF_V3/MR/复合指标
```

## 10. 当前代码迁移判断

当前已经开始做模块一部分，但还没达到完整 6 模块系统。

当前已有：

1. `pageData/` 初步建立了 PageDataPackage、cache、loader、manager。
2. 历史页加载已经开始准备 displayRows/warmupRows/lookaheadRows/calculationRows。
3. MR/MMF_V3 已经开始读取 calculationRows。

当前不足：

1. 数据分页模块还在右侧面板里，没有独立成 `pagePartition`。
2. 计算管理模块还没有独立成 `pageCalculation`。
3. 指标计算模块还没有 registry/plugin 体系。
4. 数据整理模块还没有统一 assembler。
5. 窗口管理模块还没有做。
6. 指标加载限制模块还没有做。
7. KLineChart 仍然接收整页 displayRows，不是 budgeted render slice。

## 11. 建议落地顺序

### 第一阶段：拆出数据分页模块

把右侧面板里的分页生成逻辑迁到 `pagePartition/`。

目标：

```text
RightDrawer 只调用 pagePartitionBuilder
不自己循环生成 pages
```

### 第二阶段：拆出数据计算管理模块

把 warmup/lookahead、displayOffset、barKey/sourceIndex 迁到 `pageCalculation/`。

目标：

```text
PagePartitionItem -> PageCalculationFrame
```

### 第三阶段：建立指标计算模块

建立 indicator registry。

目标：

```text
PageCalculationFrame + enabledIndicators -> PageIndicatorTables
```

### 第四阶段：建立数据整理模块

把 frame + indicatorTables 整理成 PageDataPackage。

目标：

```text
PageCalculationFrame + PageIndicatorTables -> PageDataPackage
```

### 第五阶段：建立窗口管理模块

按 visibleRange 输出 ChartRenderSlice。

目标：

```text
PageDataPackage + visibleRange -> ChartRenderSlice
```

### 第六阶段：建立指标加载限制模块

为 MR、VWAP、MMF_V3 建立渲染预算。

目标：

```text
ChartRenderSlice -> BudgetedRenderSlice
```

### 第七阶段：改造 KLineChart 渲染

KLineChart 只渲染 ChartRenderSlice。

目标：

```text
BudgetedRenderSlice -> KLineChart
```

## 12. 验收标准

1. 打开历史第 2 页前，系统已经能准备对应 PageDataPackage。
2. PageDataPackage 中有 displayRows、warmupRows、lookaheadRows、calculationRows、displayOffset。
3. 每根 K 线都有 barKey。
4. 每个指标输出都能按 barKey 或 displayOffset 对齐。
5. 缩放/拖动不触发页级指标重算。
6. KLineChart 不再负责复杂指标计算。
7. 切回已准备好的历史页时直接复用 PageDataPackage。
8. 窗口只拿当前需要渲染的 rows + indicator rows。
9. MR 一次最多渲染预算内的区间段，例如 50 段。
10. VWAP 大范围缩小时必须降级或限制点数/填充。
11. MMF_V3 大范围缩小时必须减少 marker 绘制。

## 13. 关键结论

这 7 个方向可以形成一个完整系统。

真正的目标不是“临时给第二页补 warmup”，而是：

```text
先分页。
再建立计算上下文。
再让指标包计算。
再整理成页面数据包。
再由窗口模块切片。
再由指标加载限制模块裁剪渲染量。
最后交给 KLineChart 渲染。
```

这样 K 线和指标从底层就是对齐的，KLineChart 不需要再猜、不需要再算，只负责把当前窗口画出来。
