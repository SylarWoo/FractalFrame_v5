# 12_实时尾部指标跟算模块设计

## 1. 文档目标

本文用于明确当前图表系统中以下几类职责边界：

1. 历史页指标计算
2. 准历史实时页指标结算
3. 实时尾部最后一根未收盘 K 线的实时跟算
4. 浏览器刷新恢复、周期结算、人工重算、缓存清理之间的关系
5. 指标计算模块与 KLineChart 渲染模块之间的分工

本文结论将直接约束 V2 图表系统、指标系统、realtime page、render frame 与本地恢复链路的后续实现。

## 2. 当前问题的本质

当前问题不是指标公式本身错误，而是实时链路中的状态边界不清晰。

典型表现：

- K 线尾部可以实时跳动
- 部分指标在尾部跳动时不跟
- 刷新浏览器后又恢复正常

这说明：

- 全量重建链路是通的
- 实时尾部增量计算与增量渲染链路不稳定

因此，后续必须把数据层、指标层、渲染层重新拆清楚。

## 3. 三层数据模型

系统中的 K 线与指标状态必须拆成三层：

```text
history pages
stable realtime page
tail runtime
```

### 3.1 历史页

历史页是正式历史分页结果。

特点：

- 来源于正式历史数据
- 当前系统中由 M1 拉取后聚合得到
- 按页加载
- 用户切换分页时重建当前页
- 当前页指标只需要计算一次

结论：

历史页不是缓存，而是正式查询结果。

### 3.2 准历史实时页

准历史实时页是当前周期内已经收盘、已经冻结、但尚未并入更大历史分页边界的一段中间页。

例如：

- `M5`：当日开盘后，到当前时刻之前所有已收盘的 `M5` bars
- `M30`：本周开盘后，到当前时刻之前所有已收盘的 `M30` bars

特点：

- 属于 realtime page 内部的稳定段
- 已经收盘
- 已经完成指标计算
- 不再持续跳动
- 尚未进入正式历史分页边界

结论：

准历史实时页不是普通缓存。它的准确语义是：

```text
当前周期内已结算的中间页
```

### 3.3 实时尾部

实时尾部是当前 realtime page 中最后一根未收盘 K 线。

特点：

- OHLCV 持续变化
- 指标值持续变化
- 是唯一需要 tick 级实时跟算的部分

结论：

只有这一层才是真正的运行态缓存。

## 4. 唯一真正的缓存

系统中唯一真正应该被称为缓存的，只能是：

```text
tail runtime cache
```

它表示：

- 当前最后一根未收盘 K 线的运行态
- 对应的 tail 指标运行态
- 页面短时关闭后的恢复依据

它不是正式历史数据，也不是准历史实时页文件。

## 5. 页面恢复规则

### 5.1 刚关闭页面后立刻重新打开

如果页面关闭时间很短，则：

- 历史页仍然有效
- 准历史实时页仍然有效
- tail runtime cache 仍然有效

恢复顺序应为：

```text
恢复历史页
恢复准历史实时页
恢复 tail runtime cache
继续接收 MT5 tick
```

### 5.2 隔了较长时间后重新打开

如果页面关闭时间较长，则：

- 旧 tail 很可能已经收盘
- 旧 tail 应并入准历史实时页
- 更早的数据可能已经进入正式历史页

此时不应强行恢复旧 tail cache，而应执行：

```text
重建历史页
加载当前周期准历史实时页
确定当前最新未收盘 tail
从新 tail 继续跳动
```

结论：

tail cache 只有在“当前这根 bar 仍未收盘”时才有效。

## 6. 浏览器刷新不是重算入口

浏览器刷新只允许做一件事：

```text
恢复当前状态
```

浏览器刷新不允许触发：

- 全量重算
- 重新分页
- 周期结算

硬规则：

```text
浏览器刷新 = 状态恢复，不是重算入口
```

## 7. 周期边界与正式结算

周期边界按 timeframe 独立定义：

- `M5`：每日收盘是周期边界
- `M30`：每周收盘是周期边界

周期边界是以下动作的正式触发点：

1. 当前准历史实时页冻结完成
2. 当前周期指标正式全量重算
3. 当前 realtime 周期页清空并切换
4. 下一周期 realtime page 开始

结论：

全量重算不能绑定在页面刷新上，只能绑定在周期结算点上。

## 8. 人工重算与人工结算

### 8.1 人工重算

人工重算按钮必须是显式入口。

适用场景：

- 机器中途关机
- 程序中断
- tail 结算遗漏
- 指标状态与 K 线状态脱节
- 用户怀疑当前周期指标结果被污染

规则：

- 只重算指标
- 不重新分页
- 不改变 page identity
- 不改变 bar identity
- 不做结构级重建

结论：

```text
人工重算 = 修正指标状态
```

### 8.2 人工结算

人工结算不是普通重算，它的语义应接近正式周期结算。

它可以触发：

- 当前 stable realtime page 的冻结更新
- 当前周期指标正式落盘
- tail 并入 stable realtime page

但人工结算与人工重算不能混成一个黑箱动作。

## 9. 历史页、准历史页、tail 的计算职责

### 9.1 历史页指标

职责：

- 按当前历史页计算指标
- 每次历史页切换时重建当前页结果
- 不承担实时跟算职责

### 9.2 准历史实时页指标

职责：

- 当旧 tail 收盘后，把它并入 stable realtime page
- 对新并入的 bar 做一次收盘结算
- 写入稳定指标结果

它不是实时全量重算，而是：

```text
收盘增量结算
```

### 9.3 实时尾部指标

职责：

- 只对最后一根未收盘 K 线做 tick 级更新
- 使用最小必要上下文
- 只更新 tail 对应指标结果

这是后续必须独立出来的 `tail runtime indicator` 层。

## 10. 准历史实时页必须有周期文件

准历史实时页不能只存在于内存缓存中。

原因：

1. 它已经不是纯运行态
2. 它已经收盘并冻结
3. 它在当前周期内是稳定结果
4. 如果只依赖缓存，恢复链容易把 stable 与 tail 混在一起

因此建议：

```text
每个周期拥有独立的 stable realtime page file
```

例如：

- `M5`：每个交易日一个 `stable realtime page file`
- `M30`：每个交易周一个 `stable realtime page file`

它不是“辅助缓存文件”，而是：

```text
当前周期内已结算的中间页文件
```

## 11. 三层持久化模型

建议系统按如下方式持久化：

```text
history pages
stable realtime page file
tail runtime cache
```

### 11.1 history pages

特点：

- 正式历史分页
- 按页查询
- 非缓存语义

### 11.2 stable realtime page file

特点：

- 当前周期内已收盘的 realtime bars
- 对应指标已经冻结
- 只在结算或人工重算/人工结算时更新
- 周期结束时清空并开启下一周期

### 11.3 tail runtime cache

特点：

- 当前最后一根未收盘 K 线
- 当前 tail 指标运行态
- 允许高频更新
- 页面短时关闭后可恢复
- 一旦 bar 收盘或跨周期即失效

## 12. 清理规则

### 12.1 历史页缓存清理

触发时机：

- 点击历史分页换页
- 分页索引重建
- 历史页失效

清理对象：

- history page cache
- history render cache
- history frame cache

特点：

- 可丢弃
- 可重建
- 不影响正式历史数据

### 12.2 准历史实时页清理

触发时机：

- 周期结算
- 人工结算
- 人工重算并确认覆盖

清理对象：

- 当前周期 stable realtime page file
- 对应 stable indicator snapshots
- 对应 realtime stable render caches

特点：

- 不是任意时刻清理
- 只能在周期收口或人工干预时更新

### 12.3 tail runtime cache 清理

触发时机：

- tail 收盘并入 stable realtime page
- symbol 或 period 改变
- 周期边界切换
- 恢复时发现 cache 已经过期

清理对象：

- 当前 tailRow
- tail indicator runtime state
- tail render patch

## 13. tail 跟算的最小上下文原则

tail 跟算不能默认重算整段 `activeRows`。

应按指标类型区分：

### 13.1 纯 tail 依赖型

例如：

- `Vol`
- 当前 bar 颜色
- 当前 bar 即时量价显示

依赖：

- 当前 tailRow
- 前一根已收盘 bar

### 13.2 固定窗口依赖型

例如：

- `RSI`
- `TSI`
- `VDO`
- `VMI`
- `VWAP`
- `MA`

依赖：

- 最近 N 根已冻结 bars
- 当前 tailRow

这里的 N 由指标 warmup 决定。

### 13.3 特殊结构型

例如：

- `MR_M5`
- `MR_M30`
- `MMF_V3`

这类指标允许保留专用策略，例如：

- 边界触发重算
- deferred 模式
- 专用 snapshot 计算

但也必须明确它们与 tail runtime 的边界，不能退化成“实时阶段整段全量重算”。

## 14. `Vol` 为什么最容易出问题

`Vol` 同时跨越三层：

1. K 线尾部 `volume` 会实时变化
2. `Vol` 指标直接依赖当前 bar `volume`
3. 收盘后它又必须被冻结

因此系统必须彻底分开三类动作：

- tail 跟算
- 收盘结算
- 人工重算

如果不分开，就容易出现：

- tail 跟算在改它
- 恢复逻辑又在重算它
- 全量链路又把旧值覆盖回来

这就是 `M5 Vol` 最先暴露异常的根本原因。

## 15. 状态迁移规则

### 15.1 同一根 tail 持续跳动

```text
tick 到来
-> tailRow 更新
-> tail runtime 跟算
-> 只更新 tail indicators
-> 合并进 render frame
```

不执行：

- 历史页指标重算
- 准历史实时页全量重算

### 15.2 新 bar 开始，旧 tail 收盘

```text
旧 tail 收盘
-> 旧 tail 并入 stable realtime page
-> 对新并入 stable 的 bar 做一次结算
-> stable 指标冻结并写入周期文件
-> 新 tail 初始化
-> 新 tail runtime 开始跟算
```

### 15.3 周期结算

```text
周期边界到达
-> 当前 stable realtime page 冻结
-> 当前周期指标全量重算
-> 写入周期正式结果
-> 清空当前周期 realtime page 文件
-> 开启下一周期 realtime page
```

### 15.4 人工重算

```text
用户点击重算
-> 不重新分页
-> 重新计算当前周期指标状态
-> 修正 stable/tail 指标结果
```

## 16. 指标模块与渲染模块的分工

### 16.1 指标计算模块

职责：

- 接收 K 线输入
- 计算指标值
- 输出 indicator rows / pane rows / snapshots

它不直接负责画图。

### 16.2 渲染模块

当前系统仍然可以继续使用 KLineChart 作为渲染引擎。

但 KLineChart 的职责应限制为：

- 坐标变换
- 主图/副图绘制
- tooltip / overlay / interaction 生命周期

它不应承担实时指标主计算逻辑。

正确链路应为：

```text
MT5 realtime
-> 当前 tail K 线更新
-> 指标实时计算模块
-> 生成 tail indicator rows
-> 合并进 render frame
-> KLineChart 渲染
```

而不是：

```text
MT5 realtime
-> KLineChart 隐式帮忙把指标算对
```

## 17. 打开页面速度与缓存设计

当前如果把多种不同语义的数据都当成缓存恢复，会拖慢页面打开速度。

原因：

1. 恢复阶段要判断过多混合缓存
2. 旧 tail、旧 stable、旧 page buffer 容易互相覆盖
3. 浏览器打开后还要额外做大量不必要的恢复与修正

正确方式：

- 历史页按需加载
- stable realtime page 按周期文件恢复
- 只把最后一根 tail 当作运行态缓存恢复

这样页面打开时的恢复链会明显变短。

## 18. 当前架构升级方向

系统需要从“混合 realtime 缓存 + 混合指标刷新”升级为以下结构：

```text
history indicator builder
stable realtime indicator builder
tail realtime indicator runtime
realtime indicator merger
render frame assembler
```

再配合三层存储：

```text
history pages
stable realtime page file
tail runtime cache
```

## 19. 最终硬规则

1. 浏览器刷新只恢复状态，不触发全量重算。
2. 全量重算只能来自周期结算或人工显式入口。
3. 人工重算不重新分页，只修正指标状态。
4. 历史页不是缓存，是正式分页结果。
5. 准历史实时页不是缓存，是当前周期内已结算中间页。
6. 唯一真正的缓存是当前未收盘 tail 的运行态缓存。
7. tail runtime 只允许修改最后一根未收盘 K 线的指标结果。
8. 一旦 bar 收盘，它的指标结果立即冻结，后续不能再被 tail runtime 修改。

## 20. 实施顺序

后续代码升级按下面顺序推进：

1. 先把 stable realtime page 与 tail runtime cache 拆开。
2. 再把 tail 指标计算与渲染 patch 从稳定窗口缓存中独立出来。
3. 再补周期文件、人工重算按钮、人工结算入口。
4. 最后清理旧的混合缓存与旧恢复链路。

## 21. 最终结论

本系统后续必须按以下结构实现：

```text
正式历史页：正式数据
准历史实时页：周期内已结算中间页
实时尾部：唯一运行态缓存
```

在这个结构下：

- 历史页一次性计算
- 准历史实时页在收盘时一次性结算
- 只有最后一根 tail 持续跟算

这样既能保证性能，也能让 `Vol`、`VWAP`、`VDO`、`VMI`、`RSI`、`TSI`、`MA` 等 tail 相关指标在运行过程中保持一致性。
